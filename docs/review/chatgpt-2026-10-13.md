> **项目名称：** Meshlet  
> **产品定位：** Self-hosted Private Networking  
> **产品口号：** Your network. Your rules.  
> **设计状态：** Architecture Draft 0.1  
> **目标读者：** Code Agents、架构审查者、实现工程师  
> **首要目标：** 在编写大量代码之前，统一产品边界、网络模型、安全模型、模块职责和验收标准。

## 1. 项目概述

### 1.1 产品定位

Meshlet 是一个基于 Rust 的自托管私人虚拟网络工具。

用户准备一台拥有公网 IPv4 地址的 VPS，在 VPS 上部署 Meshlet Server，然后在个人电脑、家庭服务器、办公室电脑以及其他 Linux/Windows 设备上安装 Meshlet Agent，即可建立一个由自己管理的私人网络。

用户能够：

- 通过稳定的虚拟 IP 访问网络内的其他设备。
- 访问不同地点的真实局域网。
- 通过 Alias 访问存在网段重叠的异地局域网。
- 通过 Web 控制台管理网络、设备、路由和地址映射。
- 查看连接状态、诊断网络故障并撤销设备访问权限。
- 在自有基础设施上运行控制平面和网络中继，不依赖第三方 SaaS 控制服务。

### 1.2 核心设计原则

1. **Self-hosted first：** 用户自行部署和控制服务端。
2. **Simple first：** 第一版以 VPS 为中心，不实现复杂的 P2P 网络。
3. **Mature transport first：** 复用 WireGuard，不自研加密隧道协议。
4. **Explicit routing：** 虚拟 IP、LAN 路由、Alias 路由均有明确的数据模型。
5. **Fail safely：** 配置失败不能留下不可控的网络状态。
6. **Observable by default：** 用户能够知道连接为何成功或失败。
7. **Security by design：** 设备身份、网络成员关系和管理授权必须从第一版开始设计。
8. **Incremental architecture：** 先实现可靠的单 VPS 版本，再考虑性能优化。

### 1.3 第一版不做什么

明确排除以下范围：

- 公共中继网络和陌生用户之间的资源共享。
- 区块链、代币、贡献积分和经济结算。
- 自研 WireGuard 替代协议。
- 复杂的多跳中继网络。
- 自动 NAT 打洞、P2P 直连及动态中继切换。
- 通用远程桌面、远程执行、运维任务调度平台。
- 企业级组织目录、复杂计费和多租户 SaaS 平台。
- 全局互联网出口 VPN。
- 任意 Layer 2 以太网广播和二层网络桥接。
- DNS 服务作为第一版的强制依赖。

这些功能不属于第一版验收范围。后续是否实现应另行评估。

## 2. 用户场景

### 场景 A：两台设备通过虚拟 IP 通信

设备 A：

- 所在位置：家庭
- Meshlet 虚拟 IP：`10.240.0.2`

设备 B：

- 所在位置：办公室
- Meshlet 虚拟 IP：`10.240.0.3`

VPS：

- 公网 IP：`203.0.113.10`
- Meshlet 虚拟 IP：`10.240.0.1`

设备 A 访问 `10.240.0.3` 时，数据通过 VPS 中继到设备 B。

第一版不要求 A 与 B 之间存在直接公网连接。

### 场景 B：访问异地局域网

家庭 LAN：

`192.168.10.0/24`

家庭网关设备通过 Meshlet 发布这个 LAN 路由。

办公室设备可以访问：

- `192.168.10.10`
- `192.168.10.20`

前提是办公室自身不存在同样的路由冲突，并且家庭网关能够正确转发流量。

### 场景 C：访问重叠网段

家庭和办公室都使用：

`192.168.1.0/24`

家庭 NAS：

`192.168.1.10`

办公室服务器：

`192.168.1.10`

由于地址重叠，不能单纯依靠普通 IP 路由区分两个目标。

Meshlet 允许用户为两个 LAN 分配不同的 Alias 前缀：

| 目标 | 实际 LAN 地址 | Meshlet Alias |
|---|---|---|
| 家庭 NAS | `192.168.1.10` | `10.241.1.10` |
| 办公室服务器 | `192.168.1.10` | `10.242.1.10` |

访问 `10.241.1.10` 时，由家庭网关执行地址转换；访问 `10.242.1.10` 时，由办公室网关执行地址转换。

Alias 是网络路由和地址转换功能，不只是一个名称别名。

### 场景 D：通过控制台管理设备

用户登录 Web 控制台后，可以：

- 创建网络。
- 添加设备。
- 查看设备在线状态。
- 为设备分配固定虚拟 IP。
- 配置 LAN 路由。
- 配置 Alias 前缀。
- 撤销设备权限。
- 检查配置应用状态。
- 查看故障诊断结果。

### 3.2 控制平面与数据平面

**控制平面负责：**

- 用户认证和管理授权。
- 网络、设备和网段的元数据。
- 设备身份与公钥管理。
- 虚拟 IP 分配。
- LAN 路由和 Alias 配置。
- 配置生成、版本控制和下发。
- 数据平面配置应用及错误状态。
- 诊断和审计。

**数据平面负责：**

- WireGuard 加密隧道。
- Linux 内核路由和转发。
- 必要的防火墙规则。
- Alias 的地址转换。
- 网络数据包的实际转发。

**客户端 Agent 负责：**

- 安装、启动和管理 WireGuard。
- 建立与 VPS 的隧道。
- 应用本机路由和必要的网络规则。
- 作为可选 LAN 网关发布本地网段。
- 报告隧道、路由和配置状态。
- 在配置失败时回滚由自身管理的网络修改。

控制平面不应逐包代理用户的数据流量。

### 3.3 部署形态

第一版采用单 VPS 部署：

- 一个 Meshlet Server。
- 一个 Web 控制台，可以由 Server 提供静态文件。
- 一个 SQLite 数据库。
- 一个 WireGuard 数据平面。
- 多个客户端 Agent。

控制 API 与 WireGuard 可运行在同一台 VPS，但必须在逻辑上区分。

不要在第一版引入 Kubernetes、微服务集群或独立消息队列。

## 4. 技术选型

### 4.1 后端

- 语言：Rust。
- 异步运行时：Tokio。
- HTTP API：Axum。
- 序列化：Serde。
- 数据访问：SQLx。
- 初期数据库：SQLite。
- 数据库迁移：SQLx migrations。
- 日志和诊断：Tracing。
- 配置格式：TOML。
- API 文档：OpenAPI。

以上为建议选型，Code Agent 应结合项目当前代码、依赖版本和目标平台核验后再落地。

### 4.2 前端

- React。
- TypeScript。
- Vite。
- API Client 由 OpenAPI 契约生成或保持类型同步。

第一版只需要一个管理控制台，不需要独立桌面应用。

### 4.3 隧道与网络工具

- WireGuard：隧道和加密传输。
- Linux：WireGuard 内核接口优先；是否采用 `wg-quick`、Netlink 或受控系统命令，需要根据配置事务和可测试性进行选择。
- Windows：优先评估官方 WireGuard for Windows 的受支持管理方式。
- IP 转发：操作系统网络栈。
- NAT：Linux nftables 等受支持的规则管理方式。
- 防火墙：只管理 Meshlet 自己拥有的规则，避免覆盖用户现有规则。

不得把随意拼接的 Shell 命令作为核心网络配置抽象。

## 5. 核心领域模型

### 5.1 Entity 关系

```mermaid
erDiagram
    USER ||--o{ NETWORK_MEMBERSHIP : joins
    NETWORK ||--o{ NETWORK_MEMBERSHIP : contains
    NETWORK ||--o{ DEVICE : contains
    DEVICE ||--o{ DEVICE_KEY : owns
    NETWORK ||--o{ LAN_ROUTE : publishes
    DEVICE ||--o{ LAN_ROUTE : gateway
    LAN_ROUTE ||--o| ALIAS_MAPPING : has
    NETWORK ||--o{ CONFIG_REVISION : produces
    DEVICE ||--o{ DEVICE_STATUS : reports
    USER ||--o{ AUDIT_EVENT : performs
```

### 5.2 User

表示管理控制台的用户身份。

主要字段：

- `id`
- `email` 或其他登录标识
- `password_hash` 或所选认证机制的数据
- `status`
- `created_at`
- `updated_at`

第一版可以采用本地管理员账号和安全密码认证。

不需要一开始实现 OAuth、LDAP、企业 SSO 等复杂身份系统。

### 5.3 Network

表示一个相互隔离的私人虚拟网络。

主要字段：

- `id`
- `name`
- `overlay_ipv4_cidr`
- `status`
- `created_at`
- `updated_at`

要求：

- 每个 Network 有独立的网络身份。
- 网络 CIDR 创建后，默认不可直接修改。
- 修改 CIDR 必须经过冲突检查和迁移流程。
- 不同 Network 的设备默认不能互相访问。
- 设备不能因为知道另一个网络的虚拟 IP 就获得访问权限。

### 5.4 Device

表示一台加入网络的设备。

主要字段：

- `id`
- `network_id`
- `name`
- `virtual_ipv4`
- `public_key`
- `platform`
- `status`
- `last_seen_at`
- `created_at`
- `revoked_at`

要求：

- 同一网络内虚拟 IP 唯一。
- 设备公钥必须绑定明确的设备身份。
- 设备重装或密钥轮换需要有明确流程。
- 撤销设备后，服务端必须移除其有效 WireGuard Peer 和授权。
- 设备离线状态不能仅靠数据库中的旧状态判断。

### 5.5 DeviceKey

密钥信息应与设备记录分离，便于轮换和撤销。

保存：

- 公钥。
- 密钥版本或指纹。
- 创建时间。
- 撤销时间。
- 当前是否生效。

服务端不得要求客户端上传长期私钥。

### 5.6 LAN Route

表示一个设备发布的真实局域网网段。

主要字段：

- `id`
- `network_id`
- `gateway_device_id`
- `destination_cidr`
- `route_mode`
- `status`
- `created_at`

`route_mode` 可以是：

- `direct`：普通 LAN 路由。
- `alias`：通过虚拟 Alias 前缀访问。

要求：

- 一个网段必须明确由哪个设备负责转发。
- 同一网络内不能静默接受互相冲突的路由。
- 发布路由不代表系统已经成功应用路由。
- 必须区分期望状态与实际应用状态。

### 5.7 Alias Mapping

表示一个虚拟地址前缀与真实 LAN 前缀之间的映射。

主要字段：

- `id`
- `network_id`
- `lan_route_id`
- `alias_cidr`
- `target_cidr`
- `translation_mode`
- `status`

示例：

```text
Alias:  10.241.1.0/24
Target: 192.168.1.0/24
Gateway: home-gateway
```

第一版建议要求 Alias 和 Target 的 IPv4 前缀长度一致，以便进行简单、可预测的一对一地址映射。

例如：

```text
10.241.1.10 -> 192.168.1.10
10.241.1.20 -> 192.168.1.20
```

暂不支持复杂的非等长前缀映射、任意端口代理或基于 DNS 的动态映射。

### 5.8 Config Revision

每次网络配置变更生成新的配置版本。

字段：

- `id`
- `network_id`
- `revision`
- `desired_config_hash`
- `apply_status`
- `created_at`
- `applied_at`
- `error_summary`

配置应用状态：

- `pending`
- `applying`
- `applied`
- `failed`
- `rollback_pending`
- `rolled_back`

控制台不得把数据库写入成功误认为网络配置已成功生效。

## 6. IP 地址规划

### 6.1 Overlay IPv4

第一版支持 IPv4 虚拟网络。

建议默认 CIDR：

`10.240.0.0/16`

这是默认值建议，不是不可更改的协议常量。

要求：

- 创建网络时允许用户选择 Overlay CIDR。
- 选择前检查格式合法性。
- 检查网络地址、广播地址和保留地址。
- 分配地址时避免重复。
- 不允许把 VPS 的 Overlay 地址分配给普通客户端。
- 对特殊网络地址作出明确处理。

建议初始约定：

```text
VPS / Hub: 10.240.0.1
Clients:   10.240.0.2+
```

实际分配范围应根据 Network CIDR 计算，不可硬编码为所有网络共用的固定地址。

### 6.2 CIDR 冲突检测

至少检测以下冲突：

- Overlay CIDR 与 Alias CIDR 重叠。
- Overlay CIDR 与本机或 VPS 已有路由冲突。
- Alias CIDR 与另一个 Alias 重叠。
- 同一网络中的 LAN Route 冲突。
- Alias 的 Target 与所绑定 LAN Route 不一致。
- 客户端本地路由与待安装路由冲突。

对于无法从服务端获知的客户端本地路由，应由 Agent 进行二次检查并报告。

### 6.3 不要假设所有私网地址都可以直接使用

例如，客户端本身可能已经连接了：

`10.240.0.0/16`

即使 Meshlet Server 没有发现冲突，客户端也可能无法正确路由。

因此，配置验证必须区分：

1. 服务端已知的冲突。
2. 客户端本地发现的冲突。
3. 无法确认的冲突。

无法确认时应显示警告，而不是宣称网络一定可用。

## 7. WireGuard 中继网络设计

### 7.1 第一版拓扑

```mermaid
flowchart TB
    A["Client A"]
    B["Client B"]
    C["LAN Gateway"]
    HUB["VPS WireGuard Hub"]
    LAN["Remote LAN"]

    A <-->|WireGuard| HUB
    B <-->|WireGuard| HUB
    C <-->|WireGuard| HUB
    C --> LAN
```

所有客户端只需要建立到 VPS 的 WireGuard 隧道。

客户端之间的通信由 VPS 内核转发。

### 7.2 Peer 配置原则

VPS 为每个设备创建独立 Peer。

服务端必须能根据目标 Overlay IP 找到对应 Peer。

每个客户端必须知道：

- VPS 的公网 Endpoint。
- VPS 的公钥。
- 自己的 Overlay IP。
- 需要经隧道访问的目标网段。
- 允许使用的 DNS 配置（如果启用 DNS 功能）。

客户端的 `AllowedIPs` 必须与目标路由一致，不能简单地把所有流量都指向隧道。

第一版默认只路由 Meshlet Overlay 网络、明确发布的远端 LAN 网段以及 Alias 网段。

### 7.3 VPS 转发要求

WireGuard 负责加密和 Peer 选择，但不会自动替 Meshlet 完成所有三层路由。

VPS 必须正确配置：

- IPv4 Forwarding。
- WireGuard Peer 的 AllowedIPs。
- Overlay 网段路由。
- FORWARD 防火墙规则。
- 网络间隔离策略。
- 必要的连接跟踪和 NAT。

必须通过真实集成测试证明：

1. A 能访问 B 的 Overlay IP。
2. B 能返回 A 的响应。
3. 未授权设备不能访问受保护网络。
4. 设备撤销后，旧配置不能继续建立有效连接。

### 7.4 中继流量与 SNAT

普通 Overlay 设备之间的通信应尽可能保持原始 Overlay 源地址，不需要为了让它们互通而对所有流量做 SNAT。

访问真实 LAN 时，应单独处理 LAN 的返回路由。

不能为了图省事，把整个 Overlay 网络的所有流量无差别 SNAT 到 VPS 地址。

### 7.5 MTU

WireGuard 会增加封装开销。

Agent 和服务端需要采用可配置的 MTU 策略，并提供基本诊断。

第一版不要求自动探测所有路径的最佳 MTU，但必须避免明显不合理的 MTU 配置，并能解释可能的分片或大包连接问题。

### 7.6 中继能力边界

第一版依赖 VPS 转发，因此：

- VPS 必须允许相关 UDP 流量。
- VPS 需要有足够的网络带宽。
- VPS 中断时，跨设备连接可能中断。
- VPS 不可用时，控制台和配置管理也可能不可用。

这属于第一版明确接受的可用性限制。

## 8. 异地 LAN 路由设计

### 8.1 发布路由

例如家庭网关设备发布：

`192.168.10.0/24`

其他客户端的路由表需要把这个网段指向 Meshlet 隧道。

家庭网关需要启用 IPv4 转发，并允许相应的转发流量。

### 8.2 返回路由

这是 LAN 路由最容易出问题的部分。

远端 LAN 主机收到来自 Overlay 网络的连接时，不一定知道如何返回 Overlay 网段。

支持两种方式：

**模式 A：真实双向路由**

用户在 LAN 路由器中配置返回路由，将 Overlay CIDR 指向 Meshlet 网关设备。

优点：

- 保留真实源 IP。
- 日志和访问控制更清晰。

缺点：

- 用户必须能够管理 LAN 路由器。
- 家用路由器可能不支持自定义静态路由。

**模式 B：受控 SNAT**

LAN 网关将来自 Overlay 的流量 SNAT 成 LAN 网关自身的 LAN 地址。

这样 LAN 主机可以把响应发回网关，由连接跟踪完成反向转换。

优点：

- 更适合普通家庭网络。
- 不要求每个 LAN 主机知道 Overlay 网段。

缺点：

- LAN 主机看到的来源通常是网关，而不是原始客户端。
- 基于客户端源 IP 的 LAN 访问策略会受影响。

第一版建议在 LAN Route 配置中明确显示所采用的返回路径模式。

不能只配置出站路由而忽略返回路由。

### 8.3 路由冲突

当客户端本地 LAN 和远端 LAN 都使用：

`192.168.1.0/24`

客户端无法通过同一个目的网段明确区分两个位置。

此时不能静默安装一条普通 `192.168.1.0/24` 路由并期待它自动解决冲突。

系统应提示用户为远端 LAN 配置 Alias。

## 9. Alias 地址映射设计

### 9.1 产品语义

Alias 为一个真实 LAN 提供独立的虚拟地址前缀。

示例：

```text
Alias Prefix: 10.241.1.0/24
Target Prefix: 192.168.1.0/24
Gateway: home-gateway
```

客户端只需要访问 Alias 地址。

实际 LAN 地址由对应网关负责转换。

### 9.2 映射规则

对等长 IPv4 前缀，转换可以采用前缀替换：

```text
10.241.1.10 -> 192.168.1.10
10.241.1.20 -> 192.168.1.20
```

转换前必须确认：

- Alias 地址位于已分配前缀内。
- Target 地址位于目标 LAN 前缀内。
- Alias 前缀没有与 Overlay 或其他 Alias 冲突。
- 目标 LAN 由指定的有效网关发布。
- 发起连接的设备有权访问该 LAN。
- 地址转换规则已经成功应用。

### 9.3 Alias 流量路径

```mermaid
sequenceDiagram
    participant A as Remote Client
    participant H as VPS Hub
    participant G as LAN Gateway
    participant L as LAN Host

    A->>H: Destination 10.241.1.10
    H->>G: Forward to Alias Gateway
    G->>G: DNAT 10.241.1.10 to 192.168.1.10
    G->>G: Apply SNAT if configured
    G->>L: Forward packet to 192.168.1.10
    L-->>G: Response
    G->>G: Reverse connection-tracked NAT
    G-->>H: Return to Overlay
    H-->>A: Deliver response
```

### 9.4 推荐的第一版实现方式

Alias 优先在目标 LAN 网关上实施转换，而不是让 VPS 盲目猜测目标 LAN 的实际拓扑。

原因：

- 网关知道真实 LAN 的出口。
- 网关可以直接访问目标主机。
- 可以在 LAN 网关执行受控 DNAT/SNAT。
- 不必在 VPS 上建立所有远端 LAN 的复杂重叠路由。

VPS 仍然需要知道 Alias 前缀对应哪个网关 Peer，才能把目标流量转发给正确的网关。

### 9.5 DNAT 与 SNAT

仅 DNAT 通常不够。

假设客户端 `10.240.0.2` 访问 Alias `10.241.1.10`，网关把目的地址转换为 `192.168.1.10`。

如果 LAN 主机的返回路由不指向该网关，它可能把响应发往默认路由，而不是 Meshlet。

因此第一版的默认兼容模式应允许对进入 LAN 的 Alias 流量执行受控 SNAT。

这会导致 LAN 主机看到的源地址是网关的 LAN 地址。控制台必须明确显示这一限制。

如果用户配置了正确的返回路由，并且网络条件允许，可以支持保留原始源地址的模式。

### 9.6 Alias 协议兼容边界

Alias 解决的是 IP 地址映射和路由问题，不代表所有应用协议都能透明工作。

第一版目标是常见的 TCP、UDP 和 ICMP IPv4 通信，但需要针对实际系统行为进行验证。

必须注意：

- 依赖源 IP 的访问控制可能受到 SNAT 影响。
- 直接使用真实 LAN IP 的应用仍然可能遇到路由冲突。
- 广播、组播和依赖二层发现的协议不保证跨网段工作。
- 某些应用在协议负载中携带自身 IP 地址，可能无法适应简单的地址转换。
- Alias 不是完整的二层桥接，也不是通用应用层代理。

第一版不得宣称对所有协议完全透明。

## 10. 配置状态机与事务应用

### 10.1 为什么需要状态机

当用户修改设备、LAN Route 或 Alias 时，配置至少需要经过三个步骤：

1. 更新期望配置。
2. 验证配置并生成新版本。
3. 将配置应用到实际网络环境。

数据库写入成功并不意味着 WireGuard、路由或 NAT 规则已经生效。

### 10.2 推荐流程

```mermaid
flowchart TD
    A["User submits change"]
    B["Validate domain rules"]
    C{"Valid?"}
    D["Reject with clear error"]
    E["Create desired revision"]
    F["Compile network config"]
    G["Apply to OS / WireGuard"]
    H{"Applied?"}
    I["Mark revision applied"]
    J["Rollback or reconcile"]
    K["Record failure and expose diagnostics"]

    A --> B --> C
    C -- No --> D
    C -- Yes --> E --> F --> G --> H
    H -- Yes --> I
    H -- No --> J --> K
```

### 10.3 应用策略

- 配置应用必须幂等。
- 重复执行同一个版本不得破坏网络。
- 应用失败必须保留明确的错误信息。
- 可恢复的失败应尝试回滚或重新协调。
- 不能确认是否成功时，应进入明确的未知或失败状态。
- 不得通过简单删除所有系统路由来回滚。
- 所有修改必须限制在 Meshlet 自己管理的网络对象内。

### 10.4 并发修改

同一个 Network 的配置修改必须具有版本顺序。

避免两个并发操作交叉修改 WireGuard Peer、路由或 NAT 规则。

可以采用数据库版本号、乐观并发控制或网络级互斥机制。实现方式由 Code Agent 评估，但不能完全不处理并发。

## 11. 身份、认证与授权

### 11.1 两类身份必须分开

**控制台身份：**

代表有权管理 Meshlet 的用户。

**设备身份：**

代表一台能够加入 Overlay 网络的设备。

两者不是同一种凭证。

控制台用户可以有权管理多个设备，但设备本身不能因为拥有有效 WireGuard 密钥就自动获得管理 API 权限。

### 11.2 设备加入流程

推荐的基础流程：

1. 管理员在控制台生成一次性邀请。
2. 邀请具有明确的目标 Network、有效期和使用次数。
3. 客户端使用邀请发起加入请求。
4. 客户端在本地生成 WireGuard 密钥对。
5. 服务端验证邀请并创建 Device 记录。
6. 服务端为设备分配虚拟 IP。
7. 服务端登记设备公钥。
8. 服务端更新 WireGuard Peer。
9. 客户端获得所需的网络配置。
10. 客户端验证配置并建立隧道。

私钥始终留在客户端。

### 11.3 邀请安全

- 邀请 Token 必须使用安全随机数生成。
- 服务端数据库只保存 Token 的安全摘要，或使用等效的防泄漏存储方式。
- 邀请应支持过期、撤销和一次性使用。
- 邀请不应在日志中以明文输出。
- 邀请使用过程应避免重复消费和并发竞态。

### 11.4 控制台安全

- 所有管理 API 必须认证。
- 所有敏感操作必须授权。
- 密码必须使用成熟密码哈希方案保存。
- 登录接口需要速率限制。
- Cookie 会话必须设置适当的安全属性。
- 使用 Cookie 认证时必须考虑 CSRF。
- 生产环境必须使用 HTTPS，或明确规定由受信任的 HTTPS 反向代理终止 TLS。
- 不能将默认管理员密码硬编码进程序。
- 不应将管理 API 无认证地暴露在公网。
- 关键操作应记录审计事件。

### 11.5 撤销设备

撤销设备时至少要完成：

1. 将设备标记为已撤销。
2. 使其密钥不再有效。
3. 从 VPS WireGuard 配置中移除该 Peer。
4. 移除该设备发布的有效路由。
5. 移除其相关 Alias 网关关系。
6. 应用新的配置版本。
7. 记录结果和失败原因。

如果系统无法确认撤销已经生效，必须报告失败，不能只显示“已撤销”。

## 14. Agent 与服务端通信

### 14.1 控制通道

第一版建议让 Agent 通过 HTTPS 与控制服务通信。

职责：

- 设备注册。
- 获取自身配置。
- 定期上报状态。
- 上报本地路由检查结果。
- 接收配置版本变化。
- 获取诊断任务。

不需要第一版就实现复杂的双向消息系统。

Agent 可以通过轮询或受控的长连接获知配置变化。选择方式应根据可靠性、实现成本和服务器资源进行比较。

### 14.2 配置下发原则

服务端向 Agent 下发：

- Network ID。
- Device ID。
- 本机 Overlay 地址。
- VPS Endpoint 与公钥。
- 需要安装的路由。
- LAN 网关配置。
- Alias 映射配置。
- 配置版本。
- 配置校验摘要。

不应把其他设备的私钥、管理 Token 或不必要的敏感数据下发给 Agent。

### 14.3 Agent 状态

至少包括：

- `starting`
- `connected`
- `degraded`
- `disconnected`
- `applying_config`
- `error`

具体状态应与隧道连接、路由应用、Agent 服务状态区分开。

例如，WireGuard 已连接，但 Alias NAT 规则应用失败，应显示为网络功能异常，而不是完全健康。

## 15. 跨平台网络后端

### 15.1 统一抽象

建议定义统一的网络后端接口，例如：

```rust
trait NetworkBackend {
    async fn inspect(&self) -> Result<NetworkSnapshot, NetworkError>;

    async fn apply_tunnel(
        &self,
        config: TunnelConfig,
    ) -> Result<ApplyResult, NetworkError>;

    async fn apply_routes(
        &self,
        routes: Vec<RouteConfig>,
    ) -> Result<ApplyResult, NetworkError>;

    async fn rollback(
        &self,
        revision: ConfigRevision,
    ) -> Result<ApplyResult, NetworkError>;
}
```

以上是概念接口，实际 Rust 生命周期、异步 Trait、错误类型和对象安全问题由实现阶段确认。

### 15.2 Linux Backend

负责：

- WireGuard 接口管理。
- IP 转发状态检查。
- 路由安装与删除。
- 必要的防火墙规则。
- Alias NAT。
- 规则状态检查。
- 配置回滚。

必须限制在 Meshlet 管理的规则范围内。

### 15.3 Windows Backend

负责：

- WireGuard 隧道启动与停止。
- 虚拟 IP 和路由配置。
- 系统权限检查。
- 路由冲突检测。
- 网络状态诊断。
- 配置应用失败后的清理和恢复。

Windows 的网络修改需要管理员权限时，应明确提示用户。

不得假设 Windows 与 Linux 的路由、接口命名、防火墙和权限行为完全一致。

### 15.4 平台支持策略

第一版优先验证：

1. Linux VPS Server。
2. Linux Agent。
3. Windows Agent。

其他平台应在核心架构稳定后再加入。

## 16. 安全边界

### 16.1 信任模型

默认不信任：

- 未加入网络的设备。
- 已撤销设备。
- 未授权用户。
- 用户提交的任意 CIDR。
- 未经验证的配置文件。
- 来自公网的管理请求。
- 来自 Agent 的任意路由和状态数据。

### 16.2 网络隔离

- Network 之间默认隔离。
- 设备之间的访问应符合网络成员关系和访问策略。
- 发布 LAN Route 需要明确授权。
- Alias 不能绕过路由授权。
- 不得因为某设备是 LAN Gateway 就允许其任意访问其他 Network。
- 撤销设备后，应同步清除其路由发布权限。

### 16.3 密钥管理

- 私钥仅在设备本地生成和保存。
- 私钥不写入普通日志。
- 私钥不返回给控制台前端。
- 服务端只管理公钥和 Peer 配置。
- 设备密钥轮换必须有可验证的完成状态。
- Agent 本地配置文件应采用适当的文件权限。
- 对无法安全保存私钥的平台，必须明确安全限制。

### 16.4 网络配置安全

Agent 不能无条件执行服务端提供的任意 Shell 命令。

应使用结构化配置对象表达：

- 目标网段。
- 路由动作。
- NAT 规则。
- 接口配置。
- 配置版本。

每一项都必须通过类型检查、授权检查和冲突检查。

### 16.5 审计日志

记录：

- 登录成功与失败。
- 创建、删除 Network。
- 添加和撤销设备。
- 密钥轮换。
- 添加或删除 LAN Route。
- 创建、修改和删除 Alias。
- 网络配置应用失败。
- 权限相关的敏感操作。

日志不得记录明文密码、私钥、邀请 Token 或其他长期秘密。

## 17. 可靠性与可观测性

### 17.1 日志

采用结构化日志，至少包含：

- 时间。
- 组件。
- 操作。
- Network ID。
- Device ID（适用时）。
- Config Revision。
- 错误类别。
- 操作结果。

### 17.2 指标

第一版建议关注：

- 在线设备数。
- 活跃 Peer 数。
- 最近握手时间。
- 配置应用成功率。
- 配置应用失败数。
- 路由冲突数。
- Alias 应用状态。
- 服务端流量和接口状态。

不要依赖单个指标来判断端到端网络健康。

### 17.3 故障处理

需要覆盖：

- VPS 重启。
- WireGuard 接口意外停止。
- Agent 进程崩溃。
- Agent 离线。
- 配置下发中断。
- SQLite 写入失败。
- NAT 规则安装失败。
- 本机路由冲突。
- 配置版本不一致。

服务端重启后应能够根据数据库中的期望配置重建其管理的网络状态。

客户端重启后应能够重新连接、获取配置并恢复其负责的路由。

### 17.4 数据备份

SQLite 数据库是控制平面的持久化数据源。

至少备份：

- Network 和 Device 元数据。
- 公钥与撤销状态。
- IPAM 分配记录。
- LAN Route 和 Alias 配置。
- 配置版本。
- 审计记录。

备份流程不能依赖复制正在写入的数据库文件而不考虑一致性。

恢复数据库后，系统应检查实际 WireGuard、路由和 NAT 状态，并协调到期望状态。

## 18. 测试策略

### 18.1 单元测试

重点测试：

- CIDR 解析与验证。
- IP 分配。
- 地址冲突检测。
- Alias 前缀映射。
- 网络成员授权。
- 配置版本生成。
- 配置状态机。
- 设备撤销流程。
- 错误码映射。

### 18.2 集成测试

必须验证：

1. 创建 Network 并分配 Overlay 地址。
2. 两个客户端通过 VPS 互相访问。
3. 撤销设备后无法继续通过有效 Peer 通信。
4. LAN Route 发布后可以访问远端 LAN。
5. 无返回路由时能识别或解释连接失败。
6. 启用 SNAT 后 LAN 响应能返回 Overlay 客户端。
7. 两个重叠 LAN 使用不同 Alias 后可访问各自目标。
8. Alias 冲突时配置被拒绝。
9. NAT 规则应用失败后状态准确显示。
10. 服务端重启后能恢复期望配置。
11. 客户端重启后能恢复隧道和路由。
12. 不同 Network 的设备默认无法互相访问。

### 18.3 跨平台测试

至少验证：

- Linux Agent 的路由和 WireGuard 管理。
- Windows Agent 的路由和 WireGuard 管理。
- 普通用户权限不足时的错误处理。
- 网络配置应用失败时的清理。
- 已存在本地路由时的冲突检测。

### 18.4 安全测试

- 未认证访问管理 API。
- 无权限访问其他 Network。
- 过期邀请重复使用。
- 撤销设备继续使用旧配置。
- 恶意或非法 CIDR 输入。
- 路由冲突和 Alias 前缀冲突。
- 重复请求和并发配置修改。
- 日志中是否泄漏敏感信息。

## 19. 分阶段实施计划

### Phase 0：仓库与架构审查

- 明确各平台的权限和部署要求。

交付物：

- 架构审查报告。
- 风险清单。
- 领域模型。
- API 初稿。
- WireGuard 配置原型。
- Alias 网络实验报告。

### Phase 1：最小 Overlay

目标：完成两台客户端通过 VPS 通信。

工作内容：

- Rust Server 基础。
- SQLite 持久化。
- Network 与 Device 模型。
- 设备密钥和注册流程。
- WireGuard Peer 管理。
- 虚拟 IP 分配。
- Linux 客户端基础连接。
- CLI 基础命令。
- 基本日志和状态上报。

验收：

- 两台设备可通过 Overlay IP 互通。
- Server 重启后可以恢复 Peer。
- 撤销设备后 Peer 被移除。
- IP 分配没有重复。
- 基本连接状态可观测。

### Phase 2：Web 控制台

目标：用户能够管理整个网络。

工作内容：

- 用户认证。
- React + TypeScript 控制台。
- Network 管理。
- Device 管理。
- 邀请和撤销。
- 配置版本页面。
- 基本状态和诊断页面。

验收：

- 不需要手工修改数据库即可完成基本网络管理。
- 权限和认证正确。
- 配置失败在控制台可见。

### Phase 3：LAN Subnet Routing

目标：通过远端网关访问真实 LAN。

工作内容：

- LAN Route 数据模型。
- 网关设备配置。
- Linux 转发和路由。
- 返回路径模式。
- CIDR 冲突检测。
- LAN 访问诊断。
- Windows 路由处理。

验收：

- Overlay 客户端可以访问远端 LAN 主机。
- 不支持的路由条件会被识别。
- 不会因添加一条路由而静默覆盖已有冲突。

### Phase 4：Alias Routing

目标：支持重叠 LAN 网段。

工作内容：

- Alias 数据模型。
- Alias 前缀分配。
- 前缀冲突检查。
- 网关 DNAT/SNAT。
- NAT 规则所有权和清理。
- Alias 状态展示。
- 对真实网络拓扑进行集成测试。

验收：

- 两个同为 `192.168.1.0/24` 的远端 LAN 能通过不同 Alias 访问。
- 删除 Alias 后相关规则被清理。
- 规则应用失败时系统不报告成功。
- 默认 SNAT 模式的限制在 UI 中清晰可见。

### Phase 5：稳定性与发布

目标：使项目达到可供用户部署的状态。

工作内容：

- 自动化测试。
- Linux/Windows 安装流程。
- 服务自启动。
- 配置备份和恢复。
- 安全检查。
- 诊断完善。
- 文档和示例。
- 发布流程和版本管理。

验收：

- 新用户能从空 VPS 完成部署。
- 能添加设备并建立网络。
- 能配置 LAN Route 和 Alias。
- 能诊断典型连接故障。
- 重启和配置失败不会导致不可控的网络修改。

## 20. Code Agent 协作规则

### 20.1 开始实现前

Code Agent 必须先检查仓库的真实内容：

- `Cargo.toml`
- 现有源代码。
- README。
- CI 配置。
- 已有架构文档。
- 已有依赖和平台支持。

不能假设仓库一定为空，也不能假设上述建议已经在代码中实现。

### 20.2 必须先提交架构审查结论

Agent 应回答：

1. 现有代码与本设计的差距是什么？
2. WireGuard Peer 和路由模型是否可行？
3. VPS 是否能够正确转发 Peer 之间的流量？
4. Alias 的 DNAT/SNAT 应该部署在哪个节点？
5. Windows 路由和 WireGuard 管理方式是什么？
6. 配置应用失败时如何回滚？
7. 哪些设计需要调整，为什么？
8. 哪些风险需要通过原型验证？

### 20.3 不允许的实现方式

- 不得用模拟状态代替真实网络功能。
- 不得只写 UI 而不连接后端。
- 不得只更新数据库就显示配置成功。
- 不得忽略 Windows 与 Linux 的差异。
- 不得通过删除所有路由或防火墙规则来回滚。
- 不得把私钥存入服务端数据库。
- 不得默认开放所有设备之间的所有流量。
- 不得擅自增加公共中继、P2P 穿透或复杂多跳功能。
- 不得在未经审查的情况下引入大型依赖或新基础设施。
- 不得把 TODO 或假实现描述为已经完成。

### 20.4 每个阶段的交付要求

每个阶段必须包含：

- 实际修改的文件清单。
- 架构决策和取舍。
- 实现说明。
- 单元测试。
- 必要的集成测试。
- 测试执行结果。
- 已知限制。
- 下一阶段建议。

不能仅以“编译成功”作为网络功能完成的证明。

## 22. 第一版最终验收标准

只有满足以下要求，才能认为 Meshlet 第一版达到核心目标。

### 产品

- [ ] 用户可以在自己的 VPS 部署服务端。
- [ ] 用户可以通过 Web 控制台创建和管理网络。
- [ ] 用户可以注册、查看和撤销设备。
- [ ] 用户可以管理稳定的 Overlay IPv4 地址。
- [ ] 用户可以查看配置应用状态和网络诊断。

### Overlay 网络

- [ ] 两个客户端可以通过 VPS 互相访问。
- [ ] WireGuard Peer 配置正确。
- [ ] VPS 路由和转发正确。
- [ ] 网络成员之间的授权边界有效。
- [ ] 服务端重启后能够恢复期望状态。

### LAN 路由

- [ ] 用户可以指定 LAN 网关并发布 CIDR。
- [ ] 远端客户端可以访问发布的 LAN。
- [ ] 返回路由或 SNAT 方式正确配置。
- [ ] CIDR 冲突会被识别。
- [ ] 撤销网关后相关路由不再有效。

### Alias

- [ ] 两个重叠 LAN 可以使用不同 Alias 前缀访问。
- [ ] 地址转换和返回路径正确。
- [ ] Alias 前缀冲突会被拒绝。
- [ ] 删除 Alias 会清理相关路由与 NAT 规则。
- [ ] 配置失败时控制台显示失败，而不是虚假的成功状态。

### 安全与可靠性

- [ ] 管理 API 受到认证与授权保护。
- [ ] 设备私钥不会上传到服务端。
- [ ] 邀请可过期、撤销并防止重复消费。
- [ ] 撤销设备会移除有效 Peer 和授权。
- [ ] 配置应用具有幂等性。
- [ ] 回滚不会破坏用户不属于 Meshlet 的网络配置。
- [ ] 诊断结果能区分隧道、路由、转发和 Alias 故障。

## 23. 给 Code Agent 的首轮任务

不要直接开始实现所有功能。

第一轮只执行以下工作：

1. 审查仓库现状。
2. 将当前文档与实际代码对照。
3. 验证 WireGuard 中心转发拓扑。
4. 使用实验环境验证 Alias 的 DNAT/SNAT 和返回路径。
5. 检查 Windows 与 Linux 的配置管理差异。
6. 提出必要的架构修正。
7. 输出更新后的模块图、数据模型、API 契约和 ADR。
8. 给出可执行的分阶段实施计划。

完成首轮审查后，再决定哪些设计可以直接实现，哪些必须先通过原型实验。

**Meshlet 第一版的成功标准不是功能数量，而是用户能否用自己的 VPS 稳定地连接设备、访问异地 LAN，并可靠地处理重叠网段。**
