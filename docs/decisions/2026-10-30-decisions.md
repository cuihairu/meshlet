# Meshlet 待决策与阻塞项建议

分析日期：2026-10-30。仓库基线：`a11d376fc52630e3ed285854091065ef0f648649`。

本报告完整读取根目录 `todo.md`（213 行）；未找到其他项目自身的 `todo.md` / `TODO.md`。历史归档不作为当前任务清单。对当前清单内所有 BLOCKED、待决策、需要用户提供环境或执行验收的内容作了归并，也纳入了已勾选父项中尚未解决的子问题。共形成 10 项决策，逐项给出推荐、四条理由、后续立即动作和明确延后事项。

**本次仅作只读分析并写本报告。下面的"立即动作"是采纳建议后的执行清单，未实际安装、重启、开端口、连接远端机器、修改仓库或执行验收。** 仓库记载的远端环境和历史测试结果没有在本次重新核实。工作量使用相对大小，不编造工时或费用。

## 先理解三个判断方法

1. **把"缺选择""缺资源""缺证据"分开。** 托盘用什么方案属于选择；能否重启 Windows 属于资源与操作条件；连续运行数周属于证据。继续写代码不能代替提供机器或等待时间。
2. **比较下一步能减少多少不确定性。** 先用一台机器验证安装、权限和恢复，比同时增加 MSI、多个界面框架更容易知道问题在哪里。
3. **完成标准必须对应用户真正获得的能力。** 编译成功不等于网络通，安装成功不等于托盘出现，登录后启动不等于开机无人登录也能恢复。

## D1：Windows 验收机究竟还缺什么？

**来源：** R-05 与旧巡检（`todo.md:26`）、10 月 30 日 openclaw 真机线索（`todo.md:211`）。

**推荐决策：** 先联系 openclaw 机主确认能否作为隔离验收机；符合条件就复用，不符合再提供专用 Windows 机器。保留 WireGuardNT 既定路线。旧巡检称"缺机器"，新记录已出现真机，应把当前问题细化为"该机器是否获准安装驱动、提权和重启"。出现机器名称本身不代表这些条件已满足。

**理由：**

- **成本：** 复用候选机可减少新建环境和重复配置；但要先盘点现有隧道，避免接管正在用的连接。
- **收益：** 同一台机器可以连续完成隧道生命周期、权限提升、开机恢复、安装包和托盘验收，减少跨环境排错。
- **风险：** 文档说该机已有 `WireGuardTunnel$wg-meshlet`，却没有 agent；直接覆盖容易把原来的手动隧道误当成新程序的成功。
- **决策思路：** 先确认资源是否能用于目标测试，再采购或开发；"有 Windows"与"允许做完整验收"是两件事。

**立即动作：** 由机主一次性填写：系统版本、机器用途、管理员权限、驱动安装许可、可重启时间、现存隧道是否必须保留、失败后如何恢复访问。满足条件后准备独立测试隧道名和测试网段，并按 [R-05 手动清单](/implementation/r05-windows-acceptance)安排执行。无需在聊天中提交密码或私钥。

**明确不做／延后：** 不恢复已永久停用的 win-worker；不未经确认重启 openclaw；不以 Windows CI 编译通过替代实机验收；不重新争论已经确定的隧道技术选型。

## D2：何时让 Windows agent 真正应用网络配置？

**来源：** R-05 / #52、M5 完成审计；当前 SystemBackend 别名（`crates/meshlet-network/src/lib.rs:49`）。SystemBackend 可以理解为"程序默认调用的网络执行入口"，目前非 Linux 平台仍指向明确报不支持的后端。

**推荐决策：** 保留默认拒绝；先在真机验收已有原语，再在受控候选版本中实现 Windows 后端的组合接入，最终以完整 agent 的提权、网络应用、重启恢复验收决定是否默认启用。不要把"尚未默认接入"误解为永远不能开发接入实现。

**理由：**

- **成本：** 组合接入有实际开发和验收工作；已有 `windows_tunnel` 等模块可复用，不能只改一个平台别名。
- **收益：** 按"部件可用→组合可用→默认启用"推进，既保住当前可靠边界，又能逐步形成完整产品。
- **风险：** 只装成功隧道服务仍可能缺路由、防火墙、权限或失败恢复；默认启用会把这些缺口直接暴露给用户。
- **证据更新：** M5 的旧结论曾称隧道实现整体缺席；10 月 27 日已有原语落地。当前应依据"原语存在但生命周期和完整接入未验收"决策，避免用过时结论无限阻塞。

**立即动作：** 按 D1 清单验证 install→start→stop→uninstall、重复执行与真实权限报错；为候选接入列出隧道、路由、防火墙、状态读取和清理的实现映射。区分现有 HKCU 登录启动与需要高权限的网络执行：先验证现有提权路径是否可承担目标能力，再定受管服务或执行器的必要范围。随后用候选版本验证重启后未登录的恢复、登录后 agent 收敛、撤销后不恢复旧权限，并记录结果后再作默认接入结论。

**明确不做／延后：** 不只改 `cfg` 就宣布 Windows 完成；不把不支持返回伪装成成功；不把高权限网络操作建立在可由普通用户任意替换的程序路径上；默认启用前不勾 R-05。

## D3：自动放行 ping 和设置 Private 是否继续做？

**来源：** AGENT-FW-1（`todo.md:208`）、防火墙实现（`crates/meshlet-network/src/windows_firewall.rs:116`）。

**推荐决策：** 按现有要求继续：仅对 Meshlet 隧道设置 Private，并配置受管的入站 ICMPv4 回显规则；与 D2 一起接入，但验收结果单列。当前实现用 `localip=<设备 overlay 地址>` 限定目标地址，需通过真机负例证明不会放宽其他接口，不能仅凭注释视为接口隔离已证明。

**理由：**

- **成本：** 规划与命令构造已存在，下一步价值主要在接入及真机验证，重复写同类代码收益低。
- **收益：** 新装设备能直接进行基本连通诊断，减少"隧道有了但 ping 不通"的手工排查。
- **风险：** Private 是网络信任分类，会影响既有相关策略；改错接口可能扩大其他入站流量的可达范围。
- **验收思路：** 正例证明"该通的通"，负例证明"不该新增的放行没有发生"，两者共同证明边界。

**立即动作：** D2 候选接入可用后，先保存原始网络分类和规则；按 walkthrough 的 FW-1 测试新装后远端 ping、重复 apply 不增规则、物理网卡分类不变、普通网卡地址没有因本规则获得额外放行。记录 ICMP 规则目标地址、适用范围及撤销/卸载后的清理结果。

**明确不做／延后：** 不关闭整机防火墙；不把所有接口改为 Private；不把 ping 通等同于完整访问控制通过；不在 #52 未接入时提前勾选。

## D4：Windows 托盘用什么方式实现？

**来源：** AGENT-WIN-1（`todo.md:211`）、TraySink 的现有职责（`apps/agent/src/tray.rs:39`）。

**推荐决策：** 首选 Win32 `Shell_NotifyIcon` 薄封装，复用已有四态图与状态数据，首版只做图标更新、"打开面板"和"退出"。托盘属于登录用户会话；未来高权限网络执行即使使用服务，也不由服务直接显示托盘。此项可先开发，不必等全部网络验收完成。

**理由：**

- **成本：** 功能只涉及托盘和两个菜单项，原生薄封装可避免为此引入完整窗口框架；仍需认真处理消息循环、图标资源和退出清理。
- **收益：** 复用现有状态产物，能够独立补上 Windows 没有托盘宿主的缺口。
- **风险：** PNG 文件生成成功不代表系统托盘显示成功；需覆盖会话变化、资源管理器重启和状态更新。
- **取舍：** 如果原生封装验证后明显增加维护负担，可改用 `tray-icon`；判断依据是实际代码与运行成本，而非依赖越少越好。

**立即动作：** 先明确四态到图标/文字的映射、面板入口、单实例规则及"退出"的准确效果。首版建议退出当前用户会话 agent，不顺带删除持久隧道；菜单文案需说明影响。开发最小宿主后，在真机逐态切换并检查图标、菜单、资源管理器重启后的恢复与退出清理。

**明确不做／延后：** 不重画四态图；不为首版引入完整桌面面板、设置中心或多平台 GUI 重构；不让未登录时没有托盘被误报为网络故障。

## D5：Windows 安装包选 MSI 还是 zip？还要用户提供什么？

**来源：** AGENT-WIN-2 最新进度（`todo.md:212`）、现有安装脚本（`scripts/install.ps1:1`）。

**推荐决策：** 保持已经落地的 zip + PowerShell 先行，优先真机安装验收。将验收分成"安装与自启""托盘""网络应用"三份，分别引用 D4 和 D2；旧描述"安装后 tray 出现"不能在托盘未实现时作为安装脚本唯一判据。

**理由：**

- **成本：** 清单已记载 Windows zip 发布及校验通过，改做 MSI 会增加新包装工作，不能补上缺失的托盘或网络后端。
- **收益：** 先验证现有脚本能否新装、升级并保留配置，可以最快确认真实交付链路。
- **风险：** 当前脚本安装到 `%LOCALAPPDATA%` 并登记 HKCU Run，只会在用户登录后启动；它并未交付机器级无人登录的开机恢复。
- **判断方法：** "下载到文件""程序启动""用户看见托盘""隧道可用"是四个不同观察点；分开验收才能定位失败责任。

**立即动作：** 由机主准备 `ServerUrl`、`HubEndpoint`、设备名和短期、限次 Bootstrap Token，通过本地安全方式交给脚本。按清单中的限制由用户侧执行，本次不向 Windows 机发送请求。检查进程、配置路径、注册/心跳、用户登录自启；升级前后比较配置、密钥和 token 的哈希，并核实运行进程确实使用新版本。记录没有托盘与网络不支持分别属于 D4/D2。检查 `wg.exe` 和密钥缺失时的真实行为，不只依赖脚本提示语。

**明确不做／延后：** 延后 MSI、自动驱动分发和自动升级中心；不把校验和当成发布者签名；不宣称 zip 已经具备 Windows 完整网络能力；不将 token 写入报告或公开日志。

## D6：实验环境被拆除，需要先查明责任吗？

**来源：** R-07 终局记录及用户侧动作（`todo.md:51`）；审核发现中的重复引用统一归此项。

**推荐决策：** 接受仓内已有任务日志证明"环境被主动拆除"的事实，不继续重复调查。只补齐对后续有用的输入：拆除是否符合资源使用意图、是否愿意重新保留测试环境、谁负责维护。操作者日志能够说明动作发生，不能替用户回答是否愿意恢复资源。

**理由：**

- **成本：** 反复巡检同一已销毁环境不会增加长期运行证据，消耗注意力。
- **收益：** 明确资源负责人和保留期后，重建工作才不会再次因无人知情被清理。
- **风险：** 忽略资源意图直接重建，可能再次占用原本已经回收的容量。
- **归因思路：** 环境不存在造成的 BAD 与程序故障不是同一原因，应分别记录，避免据此错误修改产品。

**立即动作：** 提供给资源负责人一条完整待答事项："是否同意为 R-07 重建隔离网格并至少保留 21 天，期间不自动清理；由谁维护？"同时确认旧 `collect.sh` / `soak.log` 是否仍保留。无需继续追问已经有日志证明的拆除时间线。

**明确不做／延后：** 未明确资源用途前不重建；不把 65 行环境缺失 BAD 当作软件失败；不尝试从仓库代码恢复已经销毁且无本地备份的容器。

## D7：长期浸泡怎样重新开始，多久才够？

**来源：** R-07 父项（`todo.md:39`）、长期浸泡与终局记录（`todo.md:46`）。

**推荐决策：** D6 资源承诺明确后，优先重建原拓扑等价的隔离测试网格（一个 hub、三个 agent；CT110–113 如未占用可复用编号），启动新的连续观察窗口。建议将"数周"落实为连续 21 天，须在启动前由验收负责人采纳；这是本报告的建议阈值，并非仓库已确定的标准。旧 39.4 小时单列为历史证据。

**理由：**

- **成本：** 需要持续保留四个测试节点及检查日志；主要投入是环境占用和日历时间，继续增加单测无法缩短这段时间。
- **收益：** 固定版本与拓扑可暴露反复重连、状态积累和意外重启等短测难以观察的问题。
- **风险：** 原环境与 cron 已停止，不能把旧窗口和新窗口相加称为连续数周；混入持续升级也会模糊稳定性结论。
- **证据边界：** 每 30 分钟采样可证明采样时刻可达，不能证明两次采样之间从未短暂断线；报告措辞必须与观测精度一致。

**立即动作：** 环境重建前保留旧日志并检查编号占用；为新运行记录版本、起点、拓扑与负责人。复用采集器前验证 PATH、关键字段和 `status=BAD` 分支。建议启动首小时人工复核、随后每日检查并把数据保存到被测环境之外。判据保留无非预期 hub 重启、无 agent 重新注册、mesh 连通，并事先确定缺样和中断的处理：中断不隐藏，定位后按约定重新起算有效连续窗口。若要求证明更细粒度连通，增加连续或更高频探测后再作对应声明。

**明确不做／延后：** 不拿旧 39.4 小时补足新窗口；不把 planned stop 混为产品故障；不在稳定观察窗口内并行做破坏性故障注入。M3 故障矩阵可在正式起算前或独立环境复跑。未满足判据不勾 R-07。

## D8：公网服务发布要改现有服务器端口吗？

**来源：** R-06 真机验收中残留的外部 BLOCKED（`todo.md:38`）。历史记录表明测试高位端口被云安全组挡住，443 已由 cockpit 占用，80 临时入口已撤销。

**推荐决策：** 先提供独立的公网测试入口，优先复用获准的空闲测试 IP/主机；无可用资源时再决定是否临时租用。按实际监听端口逐项开通测试来源，分别验收 L4、HTTP 与 TLS 直通。保持已有 cockpit 443 业务完整。

**理由：**

- **成本：** 独立入口可能增加少量资源成本与配置工作，但省去在现有业务上拆改入口及复杂回退。
- **收益：** 可清楚区分云安全组、主机防火墙、agent 监听和后端服务各层问题。
- **风险：** 共用现有 443 或长期遗留临时 80 配置，可能干扰线上业务；独立入口便于限定影响范围并回收。
- **验收思路：** 本机请求成功与公网请求成功验证的是不同路径。保留已有成功证据，只补缺失外部路径即可。

**立即动作：** 由资源负责人指定测试入口、测试域名（若验收域名路由）、测试来源 IP 和端口开放窗口。逐层核对云规则、主机规则及监听地址；从另一外部网络发送真实 TCP/UDP、HTTP、TLS 请求，并加入来源不允许、未知 SNI 的拒绝测试。TLS 核对取回的是后端测试证书。保存日志、关闭临时规则并验证入口回收。

**明确不做／延后：** 不抢占 cockpit 的 443；不将所有来源、所有端口一并开放；不把内部流量或控制面 8080 可达作为发布端口外部成功的证明；不借此扩展到 TLS 终止、自动证书等新能力。

## D9：DNS 的 15353 已测通，还需做 53 吗？

**来源：** 同一 R-06 条目（`todo.md:38`）明确记录 `0.0.0.0:53` 从未绑定，历史只验收了 UDP 15353。

**推荐决策：** 保留"内部服务目录"定位，另做一次标准 53 端口的权限与绑定验收；默认只对所需的内部/mesh 网络提供访问。若要专门覆盖历史缺失的 `0.0.0.0:53`，应在隔离节点绑定，并用外部防火墙限制入口。

**理由：**

- **成本：** 高位端口已验证解析路径，补测集中在权限、端口占用、监听与访问范围，无需重做整个 DNS 系统。
- **收益：** 能证明用户按标准 DNS 端口配置时可用，避免上线后才发现 53 已被系统服务占用。
- **风险：** `0.0.0.0` 意味着监听所有 IPv4 地址；内部目录没有必要因此暴露公网入口。
- **判断思路：** "解析逻辑正确"和"在目标部署方式下能启动"分别需要证据，高位端口通过不能推导低位端口通过。

**立即动作：** 在干净测试节点盘点 UDP 53 占用与进程权限，先设置只允许测试/mesh 来源的入口规则，再按目标部署方式启动。验证内部后缀正确响应、公共域名保持既定不应答行为、不允许来源不能访问，并记录占用和权限失败时的报错。只宣称真实测过的协议与地址范围。

**明确不做／延后：** 不上线公网递归 DNS；不覆盖现有公共 DNS；不为通过测试随意停用宿主 DNS；不因为 UDP 通过就宣称 TCP DNS 等未测能力可用。

## D10：备份恢复后，点"应用"应当修复真实网络吗？

**来源：** M3 已勾选条目内的待决策观察（`todo.md:127`）、R-07 备份恢复证据（`todo.md:42`）。幂等意味着"重复相同操作不会再做一遍"；当前对已 Applied 的修订再次 apply 会直接返回。

**推荐决策：** 当前版本保留 apply 的幂等含义，恢复合同明确为"停服务→恢复备份→启动并验证收敛"。"恢复数据库"和"系统真正可用"应显示为不同进度。未来若确需免重启修复，另设明确的"检查并修复实际状态"动作，复用恢复与授权约束，不暗改 apply 的含义。

**理由：**

- **成本：** 先使用已经有真机证据的恢复路径，避免为低频恢复场景立刻重构状态机与在线数据库切换。
- **收益：** 用户能有一条明确、可复现的恢复流程，不再期待重复点击旧修订就一定修好实际网络。
- **风险：** 仓内已记录运行中恢复可能让新写入进入被替换的旧数据库文件；仅修按钮行为无法解决这一持久化问题。
- **安全取舍：** 将来任何重放旧计划的修复动作仍须经过当前授权过滤，不能为了恢复网络把已撤销的设备权限重新打开。

**立即动作：** 采纳后将验收口径确定为：停止写入服务并确认停止，恢复库，启动服务，确认恢复执行完成，再检查 peer、路由、必要的 NAT、实际连通及已撤销设备仍被拒绝。当前没有这些结果时只说"库恢复完成"，不能说"网络恢复完成"。未来开发任务可先从清楚提示重启与恢复状态入手。

**明确不做／延后：** 不将重复 apply 偷换成强制重放；不支持未经验证的在线热恢复；延后免重启修复入口及其状态机改造；不弱化已完成的撤销权限保护。

## 建议的执行顺序与最少用户输入

两条线可以并行安排，但本报告没有执行它们：

- **Windows 线：** D1 确认可操作机器 → D5 先验安装与心跳；D4 可独立开发 → D2 验收原语、组合接入和开机恢复 → D3 验收自动防火墙 → 合并完整安装体验验收。
- **Linux 验收线：** D6 确认资源保留 → D7 重建并起算；D8、D9 在独立窗口补测；D10 采用现有恢复合同。长期窗口应尽早启动，但不能为了赶时间省略基线检查。

需要用户或资源负责人回答的内容只有以下几组；其他已有推荐，可交给实现者继续落实：

| 所需输入 | 为什么不能由代码替代 | 建议默认方向 |
|---|---|---|
| openclaw 是否可用、是否允许管理员操作/装驱动/重启 | 关系机器使用权和中断窗口 | 可隔离且可恢复时优先复用 |
| 是否重建并保留测试网格、负责人是谁 | 没有持续可用环境就没有长期数据 | 采纳连续 21 天新窗口，旧数据独立保留 |
| 是否有独立公网入口、域名与测试来源/开放窗口 | 外部可达性受资源和网络配置制约 | 独立入口、限定来源、测后回收 |
| 新设备的 server/hub 地址与注册参数 | 属于用户实际部署环境 | 本地提供短期限次 token，避免公开传递 |

选择延后资源投入也是有效决策，但其结果应写成"该能力/验收暂不承诺"，而不是将 BLOCKED 改成完成。这个区别能帮助项目避免花钱后仍不知道获得了什么，也避免因等待外部条件而重复开发已经存在的部件。
