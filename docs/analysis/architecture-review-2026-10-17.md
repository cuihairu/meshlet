# 架构与 TODO 审查（2026-10-17）

本文整理 2026-10-16 至 2026-10-17 的架构讨论，并静态核对本仓代码、部署文件及测试拓扑。它是本仓审查记录，不是外部存档提炼；建议尚未成为 Accepted ADR，也不表示功能已经实现。本次未运行网络测试或真机性能测试。

## 结论与适用范围

保留 Rust + WireGuard + 单 VPS + SQLite + Agent 期望状态对账的主架构。它适合个人设备、家庭服务器和少量异地 LAN 的自托管管理，无需引入 Kubernetes、微服务集群或公共中继运营体系。

当前实现具备基础通路，但不能沿用“只剩真实硬件走查”的整体结论：多网络资源管理、hub 重启恢复、分布式应用确认、失败恢复和正式部署权限仍有实现缺口。先补这些基础，再增加设备分组和服务转发。

最新用户需求为：不同设备与不同组组网；一台设备的指定端口或部分流量转到另一台；HTTP 使用 Nginx 做更细的路由；保持个人使用规模。相关竞品取舍见 [ZeroTier / Tailscale 调研](personal-networking-comparison.md)。

## 已有设计中应保留的部分

| 设计 | 价值 | 需要保持的边界 |
|---|---|---|
| 控制面生成计划，网络后端执行 | 便于诊断、测试与平台适配 | 管理 API 不逐包处理业务流量 |
| WireGuard 作为隧道基础 | 复用成熟加密传输 | 不自研加密协议 |
| LAN Route 与 Alias 分开建模 | 区分真实路由和地址转换 | Alias 不承担端口代理或 HTTP 路由 |
| 期望配置、修订、审计 | 能追踪变更原因 | DB、hub、设备、业务健康分别确认 |
| 注册审批与撤销 | 准入和授权有明确入口 | 撤销既影响凭据，也影响实际数据面 |
| 单 VPS、SQLite | 部署与备份负担适合个人 | 不以多租户 SaaS 的规模设计本期 |

## 当前缺口与证据

### AR-01：单实例多网络没有独立的数据面资源

`apps/server/src/revision.rs` 的 `hub_plan` 按单个 `network_id` 选择设备，但所有网络使用同一套 `DataPlaneConfig.interface`。`crates/meshlet-network/src/linux.rs` 的 `reconcile_peers` 会移除接口上不在本次计划内的 Peer。

由此推导：同一实例、同一接口交替应用 A/B 网络，会清掉另一网络的 Peer。`apps/server/tests/dual_site_end_to_end.rs` 的网络 B 由第二个服务端实例、独立 hub 密钥和独立 netns 承载，证明了该测试拓扑的隔离，不能证明生产单实例的多网络资源管理。

建议先按 Network 分配独立 WireGuard 接口、监听端口、资源所有权和隔离规则。独立接口本身不等于隔离，仍需限制跨接口转发。第一阶段在共享路由域中拒绝 Overlay、Alias、Direct 路由之间的歧义；未来需要重叠地址的独立 Network 时，再选择路由表或 netns 隔离。当前 `create_network` 仅拒绝相同 Overlay CIDR，不能代替完整重叠检查。

验收：单个生产实例同时运行 A/B；交替修改、撤销、失败恢复和重启不互相破坏；主动添加对端路由或构造越权流量仍被数据面拒绝。

### AR-02：hub 应用成功不能代表所有设备已应用

`apps/server/src/revision.rs` 在本机 hub 应用后调用 `service::settle_desired_state`。后者依靠 hub 结论与网关 `Active` 生命周期状态将路由/Alias 标为 `Applied`，没有等待网关按修订或设备计划确认。`apps/server/src/agent.rs` 的心跳携带握手与数据面概要，不包含设备应用版本、计划哈希与逐资源结果。

建议拆分期望提交、hub 应用、设备应用和业务探测结果。设备回报 `desired_revision` 对应的 `plan_hash`、应用时间和错误；网络汇总应说明哪些相关设备尚未收敛。设备离线不是已应用，也不必立即把已运行配置全部撤掉。超时、部分成功和安全策略撤销的处理需明确。

验收：hub 成功而网关离线/拒绝应用时，控制台不能显示端到端生效；乱序或旧版本回执不能覆盖新结论；业务探测失败不伪装成配置执行失败。

### AR-03：数据库恢复没有覆盖 hub 内核恢复

`apps/server/src/main.rs` 启动时加载数据库、构造后端并启动 API，没有 hub 启动对账循环。`ConfigLedger::apply` 对已 `Applied` 修订直接返回，不再执行后端。服务进程重启时内核接口可能保留，VPS 重启后则可能消失。

建议 hub 与 Agent 一样对比期望计划、上次成功计划和内核快照。启动、周期检查或明确触发时修复漂移；不能因修订簿记为 `Applied` 就跳过内核检查。配置无变化时不重置正常隧道。

验收：删除 hub 接口、路由或规则后能够恢复；VPS 重启后无需用户制造新修订；恢复失败有具体状态和诊断。

### AR-04：当前回滚是清理，不是恢复上一份可用配置

`HubDataPlaneBackend::rollback` 未使用传入修订的配置内容，而是调用 `rollback_sync`。后者移除受管接口上的 Peer/路由，并按通用 Meshlet 注释清理防火墙/NAT。范围没有细分到 Network 和具体修订产生的对象。

“只传入一个失败修订”是调用边界证据，不是资源清理边界或旧配置恢复证据。现有实现可能清掉原本正常工作的 Meshlet 配置。多网络分接口后，通用注释清理也仍可能影响其他网络的规则。

建议持久化上一份成功计划与资源清单；失败后重放该计划并读回确认。首次配置失败时清理新增对象。所有权至少区分网络、接口和资源；修订负责计划追溯，避免每次修改都重建全部稳定对象。已应用版本的撤销继续采用前滚新修订。

验收：已有 A 可用，应用 B 中途失败，恢复后 A 的业务连接可重新建立；其他网络与外来配置保持有效；恢复失败标记结果不确定，不声称回滚完成。

### AR-05：Direct LAN 的受控 SNAT 缺少执行计划

`apps/server/src/device_plan.rs` 只为 Alias 路由生成 `alias_nat_rules`，Direct 分支不生成 SNAT，也没有按 `LanRoute.return_path_mode` 编译规则。`nat.rs` 的现有 SNAT 属于 Alias 转换路径。

因此 Alias 的 `dnat_snat` 通过，不能证明 Direct LAN 的 `controlled_snat` 已实现。应分别编译与验证 Direct 双向路由、Direct 受控 SNAT、Alias 保留源和 Alias 受控 SNAT。

验收：LAN 不配置 Overlay 返回路由时，Direct 的 `controlled_snat` 可通信，且目标看到网关 LAN 源地址；保留源模式则验证静态返回路由前提。SNAT 的来源、目的、接口等匹配范围应限定在授权的 Meshlet 流量，不能误匹配本机其他业务。

### AR-06：正式服务权限与 hub 执行方式冲突

server 进程内的生产后端执行 WireGuard、路由、防火墙和 `ip_forward` 配置；`deploy/systemd/meshlet-server.service` 却使用普通用户、清空 capabilities，并限制内核参数修改。默认关闭数据面时这适用于控制面，但不能直接用于同进程 hub 数据面。

建议先提供明确、可验收的 hub 部署权限方案，说明控制面模式与含数据面模式的区别。随后可评估本机特权执行组件：通过结构化计划与受限本地接口执行，不增加远端 Shell 或任意命令通道。

验收：使用仓库正式 unit、配置和安装指南，从空 VPS 完成隧道、转发、重启恢复；不能只在 root 测试进程中证明通路。

## 新需求的领域划分

| 对象 | 职责 | 建议范围 |
|---|---|---|
| `Device` | 物理设备身份及平台能力 | 与网络成员关系解耦的候选模型 |
| `DeviceNetworkMembership` | 设备在网络内的地址、密钥、准入状态 | 一机多网时引入；跨平台逐步实现 |
| `Network` | 地址域与隔离边界 | 多 Network 不等于复杂组织体系 |
| `DeviceGroup` | 同网络内的设备集合 | 支持设备属于多个组 |
| `AccessPolicy` | 来源组/设备到目标服务的访问权限 | 初期允许规则 + 明确默认行为，不建完整策略语言 |
| `PortForward` | 入口设备监听到目标设备端口的四层转发 | TCP 先行、UDP 独立验收；来源与暴露范围明确 |
| `HttpRoute` | HTTP 域名、路径等匹配与后端 | Linux 上由受管 Nginx 执行 |

这是建议模型，不是现有 schema 或 API。当前 `Device.network_id` 为单网络直接归属，Agent 也消费单个隧道计划。一机多网涉及凭据、地址、配置目录、路由冲突与清理作用域，不只是添加组字段。

### 权限执行位置

现有 Linux `apply_routes_sync` 按隧道入/出接口宽泛 `ACCEPT`，不足以表达设备组到端口的细粒度权限。WireGuard `AllowedIPs` 提供地址与 Peer 的对应和来源校验，端口授权还需策略后端。

hub 拓扑下先在 hub 执行转发策略；入口设备和目标服务分别处理本机访问边界。未来增加 P2P 后，业务会绕过 hub，必须在端点执行同等策略再允许直连。管理用户权限、设备组网络权限与 HTTP 应用用户身份分开建模。

### 四层转发

网关选择、重复网段和端口映射的完整场景与验收已补充为 [网关、网段冲突与端口转发专题](../architecture/gateways-conflicts-and-port-forwarding.md)，区分按目标选网关、按来源选出口、端口映射和 HTTP 路由。

示例：`A:15432 → B:5432`。规则需记录入口设备、监听地址/协议/端口、允许来源、目标网络/设备/端口、源地址处理与应用状态。

必须分别覆盖外部入站和 A 本机进程访问的路径，校验端口占用、回程路由、SNAT、UDP 会话超时和删除后的清理。目标只监听 `127.0.0.1` 时不能假设远端可直接访问，可另设计目标端本地代理。

初期仅开放网络内转发；公网入口需要显式选择，不能因绑定 `0.0.0.0` 意外公开服务。跨 Network 先授权具体服务，不默认互通全部网段。“端口直接转到另一台”表达服务映射，不承诺物理 P2P；当前仍经 VPS。

### HTTP 与 Nginx

示例：`api.example.com/orders/ → B:8080`，`api.example.com/files/ → C:9000`。Nginx 按 Host 和路径匹配后代理，适合细分 HTTP 流量；参见 [请求处理](https://nginx.org/en/docs/http/request_processing.html) 与 [代理模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。

Meshlet 保存结构化对象，由入口 Agent 生成独立受管配置；先支持域名、路径前缀和单后端。应用流程应为候选配置校验、切换、平滑 reload、报告执行结果，业务可达性单独探测；参见 [Nginx 重载机制](https://nginx.org/en/docs/control.html)。

HTTPS 按 URL/Header 分流需要入口终止 TLS，证书来源、续期与私钥存储需定义；后端可再次使用 HTTPS。TLS 透传只能使用可见的 SNI/ALPN 等信息，无法读取加密路径，参见 [ssl_preread](https://nginx.org/en/docs/stream/ngx_stream_ssl_preread_module.html)。后端通常看到代理连接来源，只有可信入口写入并受后端信任的转发信息才可用于来源判定。

### 设备支持

Linux 已接入真实后端；非 Linux 的 `SystemBackend` 当前指向 `UnsupportedBackend`，Windows 路由原语不等于完整 Windows 隧道客户端。按能力声明安排角色：Overlay 客户端、LAN 网关、四层入口、HTTP 入口分别声明并验收。

先完成 Linux 和 Windows 的实际使用闭环，再按用户设备清单推进 macOS、Android、iOS。手机 VPN 接口、后台限制和发布方式需单独调研；不能直接照搬 Linux 后端。不能装 Agent 的 NAS/摄像头等可通过已有 LAN 网关接入。

## TODO 的完成口径与证据边界

当前 TODO 把历史日志、需求、实现和环境验收放在同一条超长记录中，完成口径不一致。以下旧结论需修正：

| 旧条目 | 处理 | 原因 |
|---|---|---|
| 返回路径双模式已完成 | 相关执行范围重开，关联 AR-05 | Alias 证据不能覆盖 Direct SNAT |
| 回滚安全已完成 | 资源隔离与恢复可用计划重开，关联 AR-04 | 后端参数受限不等于执行作用域受限 |
| 故障恢复已完成 | 保留数据库恢复证据，hub 内核恢复重开，关联 AR-03 | DB 状态恢复不等于内核恢复 |
| 多网络隔离已闭环 | 单实例场景重开，关联 AR-01 | 现有证据采用独立实例/netns |
| 安装只缺真实环境 | 增补 AR-06 | 正式 unit 与数据面权限存在冲突 |
| 最终验收只剩两项环境缺口 | 暂停采用该汇总 | 必须重新评估上述架构缺口 |
| 性能基准已完成 | 细分控制面与数据面 | API oneshot 基准不是隧道吞吐或连接成功率基准 |

状态使用“待设计 / 待实现 / 待验证 / 已验收 / 暂缓”；“已验收”必须限定平台、拓扑和版本。每项保留 ID、目标、依赖、当前状态、验收条件和证据链接，执行历史单独存放。

证据分为静态核对、纯逻辑/注入测试、真实内核 netns、真实设备部署。它们验证不同范围，不用测试总数替代验收。特权用例缺依赖后 `SKIP` 并返回成功时，普通 CI 绿不能证明其实际执行；应有专门的数据面门禁，强制满足前置条件并记录执行结果。

`docs/analysis/consistency-audit.md` 检查的是路径、字段和契约等机械一致性，其结论不能替代本次行为与架构审查。

## 建议实施顺序

1. P0：完成 AR-01 至 AR-06，并建立强制执行的数据面门禁；用正式服务配置验收。
2. P1：明确设备/成员/组/能力模型，完成最小组间访问策略与 Windows 客户端闭环；补连接路径诊断和实测基线。
3. P1 调研、P2 实现候选：若追求连接成功率与速度，尽早验证 UDP 受限时的回退，以及 LAN/公网端点直连；它们需要单独 ADR，不能当作几条 WireGuard 配置的小改动。
4. P2：TCP/UDP 端口转发、Nginx HTTP 路由、轻量名称解析；根据实际使用频率安排先后。
5. 暂缓：公共中继网络、L2 桥接、全局出口、企业目录/计费、完整远程运维平台。托盘与双语文档可独立推进，但不占用 P0 的验收优先级。

本顺序是个人版建议，新增能力尚未改写已有 ADR。实现前将选定方案写入新 ADR，并同步 API、数据模型、备份与迁移、诊断和验收；不把调研建议直接标记为已实现。
