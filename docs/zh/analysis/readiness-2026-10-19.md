## 「能日常使用」的定义

产品边界仍是个人自托管：不同设备、网络内分组、受控端口转发与 HTTP 服务路由（TODO.md 开头）。据此：

**最小可用集（MVP）：**自托管 Linux VPS hub；Linux agent 安装和注册；管理员自举/登录、设备审批和有范围的 API Token；版本化期望计划、应用与设备回执；恢复和回滚；私有 Overlay 连通；针对明确测试拓扑的 LAN Route/Alias；备份恢复流程；足以判断 hub、设备、业务连通状态的日志/状态；目标拓扑上的部署与数据面验收。共 **10 个具体能力组**：(1) 安装/服务端，(2) Agent，(3) 身份与注册，(4) 计划应用回执，(5) 恢复回滚，(6) Overlay，(7) LAN Route/Alias，(8) 备份恢复，(9) 状态诊断，(10) 目标拓扑部署及数据面验收。这是 Linux 个人自托管的可用切片，不等于这十组目前都已获生产验收；真实 VPS/真机走查仍待完成。

**完整可用集**在 MVP 上补齐预期个人工作流：完整验收多网络隔离与网关、冲突检测、内核执行的网段授权、Windows Agent/隧道全生命周期、经测试的 TCP/UDP 入站转发和 HTTP 路由、目标平台/设备走查，以及剩余运维验收矩阵。NAT 穿透、TCP 回退、公共中继等连接实验和 PN-10 不属于 MVP 必需项，应由实测需求决定价值。

## 推进顺序

1. 提供一台临时空 Linux VPS，先闭环 AR-06/REL-02，验证安装和服务权限边界。
2. 在该部署上逐项运行 AR-01…05 与 QA-01，保留独立结果，不用一个「能跑」结论替代。
3. 用真机走查注册、审批、应用回执、LAN 访问、撤销和重启，闭环 AR-02 与 RG-02 的环境部分。
4. 解决 RG-03 冲突语义，以及 PN-01/PN-02 的设计/实现，再扩大网段策略或宣称转发普遍可用。
5. 目标设备含 Windows 时实现并验收 PN-03；需要服务暴露时完成 PN-07/PN-08。
6. 根据真实消费者和连接需求再考虑 MOD 与 PN-04…06；MOD-05 明确为按需。

对「还要多久」的回答是依赖清单而非日期：当前 P0 剩余主要依赖环境与走查；完整个人产品仍有明确设计和实现工作。提供 VPS 后可立即闭环上列 VPS 项，但单有 VPS 无法闭环 Windows、真机、RG-03、PN-01/02 或 PN-07 剩余行为。
