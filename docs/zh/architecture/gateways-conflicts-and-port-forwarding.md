# 网关选择、网段冲突与端口转发（提案）

日期：2026-10-17。本文把用户提出的“一个网段走指定网关”“网段冲突”“某个端口转到指定电脑”整理成可区分、可验收的场景。已有基础分散在 ADR-005/006、架构审查和竞品调研中；此前尚未形成完整的场景契约。

本文是静态核对后的设计提案，不是已实现功能或 Accepted ADR；不修改代码和线上配置。依赖缺口见 [架构审查](../analysis/architecture-review-2026-10-17.md)，模块边界见 [模块化提案](modularity-and-library-design.md)。

## 1. 三类能力与当前状态

| 用户意图 | 例子 | 模型 / 当前状态 |
|---|---|---|
| 按目标网段选网关 | `192.168.10.0/24 → 家庭网关 G1`，`192.168.20.0/24 → 办公网关 G2` | 已有 `LanRoute.destination_cidr + gateway_device_id`，但 Direct SNAT、端点确认和生产恢复待补 |
| 同时访问重复网段 | 家庭和办公室都为 `192.168.1.0/24` | 已有等长 IPv4 Alias 模型与内核实验；仍需完整冲突域和生命周期验收 |
| 指定入口端口转到另一台 | `A:15432 → B:5432` | 前文已分析需求；尚无独立 PortForward API/规则执行闭环 |
| 按来源选择出口 | 来源 `192.168.10.0/24` 的流量经 G1，另一来源经 G2 | 属于来源策略路由，不由现有目的路由自动提供 |
| 所有互联网流量经指定电脑 | `0.0.0.0/0 → G1` | 属于全局出口；仍是 v1 排除项，需要另行改变范围 |

Tailscale 的 subnet router 是目标子网可达能力；Serve 则主要把本机 TCP/HTTP 服务发布到 tailnet。Meshlet 的 A 端口到 B 设备映射是独立产品需求，不能因为名称类似就认定已与 Serve 等价。[子网路由](https://tailscale.com/docs/features/subnet-routers)、[Serve TCP 转发](https://tailscale.com/docs/reference/tailscale-cli/serve)

## 2. 按目标网段选择网关

### 2.1 配置与路径

在同一 Network 中登记两个网关：G1 的 Overlay IP 为 `10.240.0.2`，G2 为 `10.240.0.3`。示例配置意图如下，地址仅为示例，使用前必须检查占用：

| 路由 | 目标网段 | 网关 | 返回路径 | 对发起端的意义 |
|---|---|---|---|---|
| home-lan | `192.168.10.0/24` | G1 | 受控 SNAT 或已配置返回路由 | 访问 `.10.x` 到家庭 LAN |
| office-lan | `192.168.20.0/24` | G2 | 受控 SNAT 或已配置返回路由 | 访问 `.20.x` 到办公 LAN |

当前 hub 拓扑下，C 访问 `192.168.10.50` 的路径是：

```text
C → WireGuard → VPS hub → WireGuard → G1 → 192.168.10.50
```

“选择 G1 网关”表示 hub 最后应把对应前缀交给 G1；不代表 C 已与 G1 物理直连。当前 C 只与 hub 建 Peer，计划编译必须让客户端路由、hub 路由、各端 AllowedIPs、网关转发规则互相一致。

`apps/server/src/service.rs::create_route` 已接受目标 CIDR 和网关 ID，验证网关属于本网络且为 Active；`apps/server/src/device_plan.rs` 已据路由和网关生成设备计划。Active 是生命周期状态，不能代替在线、LAN 可达或设备已应用确认；这些须由 AR-02 的回执和健康证据区分。

### 2.2 返回路径与适用设备

两种返回方式继续沿用 [ADR-005](../decisions/adr-005-lan-return-path.md)：

- 保留源地址：目标 LAN 必须能把 Overlay 来源路由回 G1；目标机器本身不必安装 Agent。
- 受控 SNAT：G1 把授权流量来源改为自身 LAN 地址，LAN 主机容易回复，但目标看到的是 G1，不能再用原始源 IP 做设备识别。

目前 Direct 路由没有按 `return_path_mode` 编译受控 SNAT，属于 AR-05，不能把 Alias NAT 的测试当成这里已完成的证明。

网关还必须能到达目标 LAN、有相应 IP 转发与防火墙权限。客户端和网关侧分别确认计划，展示“期望经 G1、G1 已应用、目标业务可达”三种证据。

### 2.3 重复发布、主备与失效行为

第一阶段一个可见目标前缀明确指定一个网关。两个网关发布相同 Direct 前缀时拒绝并点名冲突；同网段主备需要单独模型，不能把第二条重复路由当成自动高可用。

网关失效时报告不可达/降级，不静默切到另一个站点；相同 IP 在不同站点可能代表完全不同的设备。是否保留路由阻止默认路由兜底、停止下发新流量或选择明确的备用网关，应由失败策略统一编译与验收。不能只删路由而让私人目的意外转向普通默认出口。

若未来允许 `/16 → G1` 与其中 `/24 → G2`，需显式采用更具体前缀优先的路由语义，并规定 `/24` 失效后是否允许落回 `/16`。当前 `create_route` 对 Direct 重叠前缀采用拒绝策略，不能把操作系统本身能做的路由选择宣称为产品已支持。普通目的路由和来源/标记策略的区别参见 [iproute2 规则说明](https://kernel.googlesource.com/pub/scm/network/iproute2/iproute2/+/9c7bdc9f3328fb3fd5e7b77eb7b86f6c62538143/man/man8/ip-rule.8)。

## 3. 网段冲突按类型处理

### 3.1 两个远端 LAN 地址相同

不能仅凭 `192.168.1.50` 确定要访问哪个站点，修改 metric 也不能让同一个目的地址同时代表两个不同站点。用两个不同 Alias 前缀提供独立访问地址：

| 站点 | 真实 LAN | 访问用 Alias | 示例目标 |
|---|---|---|---|
| 家庭 G1 | `192.168.1.0/24` | `10.241.1.0/24` | `10.241.1.50 → G1 → 192.168.1.50` |
| 办公 G2 | `192.168.1.0/24` | `10.241.2.0/24` | `10.241.2.50 → G2 → 192.168.1.50` |

沿用 [ADR-006](../decisions/adr-006-alias-prefix-nat.md)：Alias 与真实前缀等长；转换在各自目标网关；hub 按 Alias 区分站点，不能将两个真实重叠前缀交给不同 Peer 作为可见转发目的。

计划必须明确区分“网关本地真实目标”与“隧道中可见前缀”。2026-10-18 复核时，`meshlet-domain/src/peer_routes.rs` 已仅在 Direct 模式发布真实目的，`device_plan.rs` 与 `revision.rs` 也按 `RouteMode` 选择真实或 Alias 前缀；此前“辅助推导仍泄漏真实前缀”的描述已过时。RG-02 仍需通过正式 API/Agent 入口同时验证双站点与客户端本地同前缀，不能只检验 UI 配置无冲突。各端地址集合和待补验收详见 [RG-02 设计](../design/overlapping-lan-alias.md)。

Tailscale 的 4via6 使用独立 IPv6 地址区分重叠 IPv4 站点，目标相同但地址表达方式不同。Meshlet 可继续保留 IPv4 Alias，不必为了功能对齐改成 4via6。[4via6 官方说明](https://tailscale.com/docs/features/subnet-routers/4via6-subnets)

### 3.2 客户端本地 LAN 与远端 LAN 相同

例如笔记本本地为 `192.168.1.0/24`，家庭远端也为该网段：保留本地原路由，远端通过 Alias 访问。不要静默覆盖本地网段、默认网关或用更具体路由抢占用户原有设备。

如果只需一个服务，也可使用独立入口端口，例如 `A:15432 → 家庭数据库`，由知道站点归属的入口/目标 Agent 完成连接。但代理所在位置必须有无歧义的目标路径，不能在同样冲突的客户端上简单改写到 `192.168.1.50` 就宣称问题解决。

### 3.3 完整冲突分类

| 冲突 | 第一阶段建议行为 | 检测位置 |
|---|---|---|
| 同网络相同 Direct 前缀、不同网关 | 拒绝，显示既有路由和网关；主备另行设计 | 控制面 |
| Direct 前缀部分包含/重叠 | 沿用保守拒绝；不自动推断优先级 | 控制面 |
| 多个 Alias 路由的真实网段重叠 | 允许真实重叠，可见 Alias 必须不重叠 | 控制面 + 计划编译 |
| Alias 与 Overlay/其他 Alias/可见 Direct 前缀重叠 | 拒绝并选择其他 Alias | 整个共享路由域，不能只检查单条记录 |
| Overlay 与本机 LAN、其他 VPN 或已占用路由重叠 | 拒绝危险应用，提示换 Overlay；Alias 不能修复所有 Overlay 冲突 | Agent 本地预检 + 服务端已知信息 |
| Alias 与客户端本地网段冲突 | 在受影响客户端阻止应用并上报，重新选前缀 | Agent；必要时影响网络级选择 |
| 不同 Network 使用重叠地址 | 共享路由域初期拒绝歧义；真正支持重叠需要独立路由上下文 | AR-01 + 多网客户端 |
| 无法确认离线设备上的本地占用 | 明确标未知；设备上线应用前再检查 | 控制台 + Agent |

现有 Linux 外来路由预检主要查询精确前缀，不等于完整检测包含关系、策略表或其他 VPN 的所有冲突；新增预检应覆盖应用实际使用的路由域。Alias 示例地址不是固定保留池，仍必须检测占用。

SNAT 解决返回路径与来源表示，不解决“同一目标 IP 指哪个站点”的歧义。DNS 名称可解析到不同 Alias，但两个名字都解析到相同真实 IP 时，普通三层路由仍不能据此识别站点。

## 4. 指定端口转到指定电脑

### 4.1 先区分三种意图

| 意图 | 示例 | 机制 |
|---|---|---|
| 访问 A 的入口端口，交给 B | `A:15432 → B:5432` | PortForward：四层代理或受管 DNAT/返回路径 |
| A 上的应用通过本地端口访问 B | `127.0.0.1:15432 → B:5432` | 本地监听代理；用户无需改为远端虚拟 IP |
| 访问外部目标的某类流量经 B 出网 | A 到某目的的 TCP 443 经 B | 策略路由/出口代理；不是入口端口映射，本期不默认承诺 |

“某端口的流量”默认指协议与目的监听端口，不按客户端随机源端口来识别某个应用。对同一个端口按 HTTP 域名/路径拆分则交给 HttpRoute/Nginx。

### 4.2 最小规则模型

以下是候选契约字段，不是已提供的 API：

| 字段 | 意义 |
|---|---|
| `network_id`、规则 ID | 所有权与授权范围 |
| `ingress_device_id` | 哪台机器承担入口，不必固定为 VPS |
| `listen_address`、`listen_port`、`protocol` | 监听在哪个地址/接口，TCP 和 UDP 分开 |
| `allowed_sources` | 允许的设备/组；外部来源需另定义 CIDR/应用认证 |
| `target_device_id`、`target_port` | 到目标设备的服务；计划阶段解析当前虚拟地址 |
| `exposure` | 本机、Overlay、指定 LAN 或显式公网 |
| `source_mode`、执行方式 | 代理源、SNAT 或保留源的明确语义 |
| `desired_revision`、设备结果、健康证据 | 配置提交、已应用与业务可达分别报告 |

目标是网关后的 LAN 主机时，应带 `gateway_device_id + 站点内目标地址`，或引用已批准的 LAN/Alias 服务对象；不能仅保存一个全局裸 IP，从而绕过站点选择和访问策略。

### 4.3 实现选择与推荐起点

| 做法 | 优点 | 必须承担的边界 |
|---|---|---|
| 用户态 TCP 代理 | 入口与本机访问路径容易统一；回程由两段连接处理 | 目标通常看到代理来源；代理也必须有正确 Overlay/站点路径 |
| 内核 DNAT + 必要的 SNAT | 可复用 Linux 网络执行器 | 入站与本机流量经过不同 hook；回程、所有权、已建立连接清理与权限更复杂 |
| HTTP Nginx | 按域名/路径路由，成熟配置校验与 reload | 只负责相应应用协议；HTTPS 路径分流需终止 TLS |

个人版可以先评估受管 TCP 监听代理，再独立实现/验收 UDP；若选择 NAT 方案，需要针对各路径验证，不能只增加一条 PREROUTING 规则。Netfilter 对本机与转发报文有不同处理路径，参见 [官方架构说明](https://netfilter.org/documentation/HOWTO/netfilter-hacking-HOWTO-3.html) 与 [nftables 手册](https://netfilter.org/projects/nftables/manpage.html)。

这是实现候选，不在此锁定新代理依赖或自研传输。用户态代理在入口机器经当前内核 WireGuard 到 B 时，该机器仍有虚拟接口；“转发运行在用户态”不等于“整个网络无需虚拟网卡”。

### 4.4 边界与失效行为

- 默认限制明确的本机或 Overlay 监听；绑定所有地址必须解释实际暴露接口，不自动等于允许公网访问。
- 监听占用需检查协议、地址、端口与通配地址关系；同端口按 HTTP Host 分流是 L7 共享监听，不是两个冲突的 TCP listener。
- B 的服务仅监听 `127.0.0.1` 时，远端 A 不能直接连接该回环地址；需 B 的本地服务发布/代理，或用户明确调整监听地址。
- 保留源模式需验证回程及 WireGuard 来源地址校验；SNAT/代理模式需显示目标实际看到的来源，不能凭伪造 Header 或未支持的 PROXY protocol 还原身份。
- UDP 需定义会话键、回复来源、空闲过期和容量；不能用 TCP 双向字节流实现替代 UDP 报文语义。
- 更新目标应明确新连接切换与存量连接排空；目标离线不能静默转到别的电脑。撤销需定义“拒绝新连接”和“终止已建立会话”的时限，精确处理自有状态，不清空系统 conntrack。
- 跨 Network 转发是显式服务授权，不能让普通映射把网络隔离边界悄悄打通。

## 5. 统一控制台与库边界

控制台分别提供“网段路由”“重叠网段 Alias”“服务映射”三类对象，避免一个“网关”开关同时承担目的路由、全局出口、NAT 和反向代理。列表应显示目标、期望入口/网关、返回方式、暴露范围、设备应用版本和健康证据。

纯计划层负责冲突分析、目标到网关选择、路由/AllowedIPs/授权的一致性；OS 后端执行路由与 NAT；服务执行模块负责监听代理/Nginx。上层控制面统一审批和修订，不在 HTTP handler 内逐包转发业务。

## 6. 验收矩阵与待办

| ID | 验收场景 | 通过条件 |
|---|---|---|
| RG-01 | 两个不同 LAN 分别指定 G1/G2 | TCP/UDP 应答携带站点标识；只到正确网关；源保留/SNAT 返回分别验证；网关离线不串站点 |
| RG-02 | 两站点相同 LAN + 本地也同前缀 | 两个 Alias 同时可达正确主机；本地设备仍可访问；客户端/hub AllowedIPs 与路由一致，不以远端真实重复前缀择站点 |
| RG-03 | 全冲突域预检 | Exact/包含/部分重叠、Overlay/Alias/Direct/外来 VPN、共享多网路由域都有明确拒绝/未知状态；不覆盖外来配置 |
| PN-07 扩展 | A 入口端口到 B 或站点内服务 | 本机/Overlay 入站分别成功；未授权来源拒绝；端口占用、回环后端、返回路径、UDP 回复和撤销已建立连接均有结果 |
| PN-08 扩展 | 同入口 HTTP 分流 | 域名/路径只到批准后端；TLS、重载失败与旧配置保持可用分别验证 |

RG-01 与 AR-05/AR-02 联动；RG-02/RG-03 与 AR-01、MOD-03 联动；PN-07/08 继续沿用现有 ID，不另起重复功能。来源选出口、全局出口和自动主备仍是待明确范围的候选，不把操作系统可能具备的能力计入本仓完成状态。
