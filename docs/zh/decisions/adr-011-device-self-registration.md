# ADR-011：设备自举注册（ZeroTier 式）与中心审批

- 状态：Accepted
- 日期：2026-10-15
- 期次：Phase 5 后续（2026-10-15 用户需求）
- 来源：用户指令（agent 需要开机执行、可配置、授权流程学 ZeroTier）
- 与 [ADR-010](./adr-010-console-auth-enrollment) 的关系：**扩展而非推翻**——ADR-010 的一次性邀请路径原样保留，本 ADR 增加一条并行的设备入口；两条路径共用同一套摘要存储纪律与 agent 凭证体系。

## 背景

ADR-010 的设备加入路径要求管理员**逐台**生成邀请并手工投递（邀请 Token 一次性、含目标 Network 与有效期）。设备批量铺开时这是逐台人工成本：每台新设备都要人在控制台上点一次、再想办法把 Token 送到设备上。零跳式（ZeroTier）网络的通行做法是把「准入」与「审批」拆开：一张长期可撤销的准入凭证让设备自助进门，管理员只在审批队列上决定放行与否。

## 问题

1. 如何让设备自助注册，同时不把数据面访问权交给自助路径本身？
2. Pending（已注册、未批准）设备如何存放？是否进 `devices` 表？
3. 批准时是否需要轮换 agent 凭证？
4. 中心如何「发指令」——是否新增即时命令通道？

## 候选方案

1. **自举码 + Pending + 中心审批（采纳）**：控制台签发长期自举码（可撤销、可选次数上限），设备持码自举注册落 Pending 队列，审批者放行或拒绝；
2. 每台设备仍用一次性邀请，但邀请改由服务端自动生成并打印（只是省了点击，投递瓶颈不变）；
3. 无审批的自助注册（持码即入网）——准入即授权，泄漏自举码等于泄漏网络访问权，与 §11.4 的「禁止共享 Token」同族风险；
4. 审批时轮换 agent 凭证——需要把新凭证再投递一次到已就位等待的设备，把审批者变成秘密搬运工。

## 决定

- **自举码**（`bootstrap_tokens` 表）是长期准入凭证，与邀请同表纪律：只存 SHA-256 摘要、原始码仅在签发响应返回一次、列表只有元数据、支持撤销与可选 `max_uses`；
- **三级状态**：`Pending`（已自举注册、未审批）→ `active`（批准）/ 清理（拒绝）。**Pending 不写入 `devices` 表**，两条理由（migration 008 表头逐条记录）：① `devices.virtual_ipv4` 为 `NOT NULL`，而虚拟 IP 在**批准时刻**才分配——批准前占地址会让管理员看到的可用容量虚低，拒绝后还得回收；② 不占地址 = 不进期望配置、不进 Peer AllowedIPs（`device_plan` 只读 `devices`），Pending 设备对数据面完全不可见；
- **批准**才是状态变更的唯一时刻：分配虚拟 IP、设备入册（`approved_at` 记审批时刻）、记录**恰好一个**修订（§10.1：写入 ≠ 生效，修订初态 `pending`）；
- **凭证不轮换**：注册期签发的 agent 凭证在批准时原样沿用（设备 id 不变，批准对设备透明）；**拒绝**才作废凭证（申请行与凭证一并清理）；
- **Pending 期可心跳**：证据（`last_report_at` / `dataplane_evidence`）落注册申请行，回执 `online_state = "pending"`；计划端点对 Pending 设备 `404` 且消息点名 `pending approval`，agent 退避重试——**身份判定先于全局数据面开关**（`503 dataplane_not_configured` 不得掩盖 pending 信号）；
- **两条错误面分离**：设备出示无效/撤销/耗尽的码 → `401 unauthorized`；管理侧对未知 id 操作 → `404 not_found`（不泄露存在性）；
- **序列按类分离**：`bootstrap_seq`（`bt-N`）与 `registration_seq`（`dev-reg-N`）为两个独立的单调计数器，前缀互不相交，按类单调即足够；
- **中心「发指令」= 期望状态 + 撤销**：不新增即时命令通道或长连接。对设备的指令全部表达为期望配置修订（设备轮询 `desired` 拉取，变更经 apply/rollback 落内核），撤除走既有 `POST .../devices/{device_id}/revoke`；
- **Agent 侧凭证解析顺序**：配置 `device_token` → `{state_dir}/device_token` → `bootstrap_token` 自举注册（成功后落盘复用）；WireGuard 密钥对本机生成（已有私钥文件只推导公钥，重装不换钥匙），私钥不出设备（ADR-010）。

## 理由

- 准入与授权分离：泄漏的自举码只能制造 Pending 排队（消耗 CPU 与一条队列行），**不能直接获得任何数据面访问权**——审批仍是唯一信任关口；
- 凭证不轮换把审批从「秘密投递」变成「控制台上一个按钮」，这是把流程做成可用的前提；
- 不新增即时命令通道意味着不引入新的长连接面、新的失效模型与新的时钟/顺序问题——现有期望状态 + 修订机制已覆盖「让设备做某事」。

## 缺点与风险

- **自举码是长期凭证**：泄漏窗口取决于撤销时效；缓解措施是控制台可随时撤销 + `max_uses` 限次 + 原始码只返回一次；风险面已限定为「制造 Pending 排队」而非入网；
- **审批队列无配额上限**：泄漏的自举码可制造任意多条 Pending 行（每行占用一行 `device_registrations` 与一个无效注册凭证）；v1 接受该风险，见重新评估条件；
- **批准前无法核实设备真实身份**：设备名与公钥均为设备自述，管理员只能人工核对；未来可能需要设备证明（attestation）或预登记指纹；
- **审批与设备 id 的耦合**：批准沿用注册期 id（`dev-reg-N`）以保证 `agent_tokens` 等外键无需迁移，代价是 id 命名空间暴露「该设备来自自举注册」；无安全影响（id 非秘密），但对外不隐藏来源。

## 重新评估条件

- Pending 队列出现规模化堆积（泄漏自举码或恶意排队），需要配额/速率限制；
- 需要多审批人/审批分级（当前单管理员一钮放行）；
- 需要证明设备真实身份而非自述（引入 attestation）；
- 引入 P2P/组播等非审批可表达的访问语义，「期望状态 + 撤销」不足以表达指令时。
